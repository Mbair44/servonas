# Employee numbering

Employee UUIDs remain the authoritative identifiers. `employees.employee_number` is a tenant-scoped, human-readable identifier generated by the database.

The allocator locks the business’s `employee_numbering_settings` row before selecting and incrementing `next_number`. This makes concurrent employee creation safe and avoids duplicate numbers. The existing case-insensitive unique index on `(business_id, lower(employee_number))` remains the final integrity boundary.

Apply and verify:

```sh
supabase db push
psql "$DATABASE_URL" -f supabase/audits/employee_numbering_verification.sql
```

Every verification query should return zero problem rows, and the final readiness query should return `true` for all three fields.

To exercise concurrency against a non-production database, open two SQL sessions, begin a transaction in both, and insert employees for the same business before committing both. Each insert must receive a different number and `next_number` must advance twice. Do not run this test with real customer data.

Changing formatting or the next sequence affects future employees only. Existing numbers are intentionally preserved. Settings changes are recorded in `employee_numbering_audit_events`.
