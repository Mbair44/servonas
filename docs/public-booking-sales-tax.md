# Public booking sales tax

Apply `20260928000300_public_booking_tax_snapshots.sql` before deploying the checkout changes. No existing booking amounts or snapshots are backfilled. New nullable inventory fields `is_taxable` and `tax_code` allow explicit exclusions/provider codes; null eligibility inherits `default_invoice_item_taxable`. Rental options, duration and operator charges inherit their parent rental's eligibility.

`/api/checkout` is the canonical route. `/api/book` and `/api/bookings` now alias it and require its tenant, policies, items, and price-review contract. Old single-item request payloads must migrate to this contract; they fail validation rather than create untaxed reservations. Reservation SQL is service-role-only after migration. The existing admin-assisted booking workflow takes explicit staff-confirmed tax amounts and is not converted to automatic pricing in this change.

Pricing order: date price → duration/multi-day/options/operators → proportional rental discount allocation (cent-exact) → rental/delivery tax eligibility → configured tax mode → total → deposit/balance. Delivery receives none of the rental discount. Manual mode uses the configured basis-point rate; automatic mode uses connected-account Stripe Tax. Automatic failures, missing address/account, missing line results, or mismatched provider totals block checkout. No manual-rate fallback exists. No-tax or exempt quotes skip the provider.

The route returns `requiresPriceReview` before making a reservation, including the server's subtotal, discount, delivery, tax, total, deposit and remaining balance. The native review dialog shows those amounts; confirmation submits accepted total/deposit. The server revalidates all pricing and recalculates tax. A changed total requires another review. Provider calculations made during review do not charge cards. Paid and invoice-later paths share this calculation. Prices shown before review are estimates.

For the reported $185 rental, $50 discount and $100 nontaxable delivery, Stripe receives a $135 taxable rental component and no delivery component. Actual tax is determined by Stripe Tax/account registrations/product code/address, not the configured 620-bps manual rate. The 8% fixture in tests is artificial.

Booking `tax_snapshot` stores settings, exemption status, per-component discounted basis and tax, provider calculation ID, address and provider details. Each booking item stores its corresponding tax line. Snapshot replacement is rejected once populated; no historical booking is recalculated. Existing payment, confirmation, balance collection and Manage Booking readers consume the persisted booking total/balance. Inclusive-tax job creation subtracts included tax from job subtotal to avoid adding it twice.

Scope boundaries: existing add-rental amendments retain their prior tax behavior, and date-change previews are not financial commits. Extending their tax handling needs an explicit amendment calculation/versioning design; this change fixes new public booking creation only. No historical corrective charge, Meta action, production migration, or Stripe payment is performed by this development work.

Validation: `node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON --test tests/bookingTax.test.ts tests/bookingTaxCheckout.test.ts`; migration test: set `PGLITE_TEST_ROOT` to an installed `@electric-sql/pglite` package and run `tests/bookingTaxDatabase.test.ts`. Checkout tests execute the real handler with mocked database/Stripe I/O. Run `npx tsc --noEmit --incremental false` for a fresh typecheck.
